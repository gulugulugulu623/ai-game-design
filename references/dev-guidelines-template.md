# DevGuidelines.md Template

Use this as a reusable template for AI-led game projects. Adapt bracketed sections to the specific project.

````markdown
# DevGuidelines

版本：0.1  
日期：[YYYY-MM-DD]  
项目：[Project Name]  
引擎：[Engine Version]  
语言：[Programming Language]  
目标平台：[Target Platform]

本文件约束 AI 在本项目中的开发行为。项目包含设计文档、规则数据、关卡/卡牌/角色/敌人/物品配置、教程文案、UI 文本和本地化内容。任何自动化修改都必须优先保护规则正确性、数据完整性和文本编码。

## 1. 编码与文本

1. 所有文本配置必须使用 UTF-8 读写，包括 JSON、CSV、TSV、TXT、YAML、Markdown、脚本和本地化表。
2. 写文件时优先使用 UTF-8 without BOM。
3. 读写文本文件必须显式指定编码，不依赖 PowerShell、CMD、Node、Python、引擎或编辑器默认编码。
4. 不要用未指定编码的 `>`、`>>`、`Out-File`、`Set-Content`、`Add-Content`、`Export-Csv` 重写配置。
5. 看到终端中文乱码时，不直接判定文件损坏。先用显式 UTF-8 读取验证。
6. 如果文件内容真的出现 `锟斤拷`、`Ã`、`�`、`閫犳垚` 等乱码特征，停止写入并报告。

## 2. 删除与清理限制

禁止批量删除文件或目录。

不要使用：

- `del /s`
- `rd /s`
- `rmdir /s`
- `Remove-Item -Recurse`
- `rm -rf`

需要删除文件时，只能一次删除一个明确路径的文件。

正确示例：

```powershell
Remove-Item "C:\path\to\file.txt"
```

如果需要批量删除文件，应停止操作，询问用户，让用户手动删除或明确授权具体删除清单。

## 3. 规则权威来源

开发规则相关功能前必须优先阅读：

1. `[Relevant Split GDD: rules/state machine]`
2. `[Relevant Split GDD: scoring/combat/economy]`
3. `[DataNamingConventions.md]`

如发现人类版 GDD、AI GDD、数据、代码实现冲突，先记录差异并报告，不要擅自让其中一个覆盖其他。

## 4. 代码约定

- 遵守项目语言和引擎的现有风格。
- 规则/模拟层不得依赖 UI 节点。
- UI 层不得直接修改核心规则状态，只能提交命令或调用公开接口。
- AI/NPC/敌人逻辑不得读取设计上不可见的信息。
- 复杂规则函数必须有测试或可复现调试用例。
- 不做与当前任务无关的重构。

## 5. 数据文件约定

1. 静态数据放在 `[data directory]`。
2. 显示文本和稳定 ID 分离。
3. JSON 修改必须使用解析器，不要用正则或字符串替换改结构。
4. 不要删除未知字段。
5. 不要为了格式统一重排全量 JSON 字段。
6. 不要把数字写成字符串，也不要把字符串 ID 自动转成数字。
7. 修改数据后必须验证：
   - 文件可解析。
   - ID 唯一。
   - 引用存在。
   - 文本字段无乱码。
   - 领域特定完整性检查通过。

## 6. 重点保护数据

以下数据属于核心资产，需要按项目替换：

- 核心规则配置。
- 数值平衡配置。
- 关卡/牌组/角色/敌人/物品定义。
- AI 行为配置。
- 教程脚本。
- 本地化文本。
- 图鉴/百科说明。
- 存档字段。

不要在未确认业务含义时修改这些内容。

## 7. 批量修改规则

1. 批量修改前确认是否已有专用脚本或工具。
2. 批量修改前确认 git 状态或备份目标文件。
3. 批量修改后至少做三类检查：
   - 编码检查。
   - 结构检查。
   - 语义抽查。
4. 不要在一次修改中同时做数据迁移、字段重命名、文本润色和数值平衡。
5. 若检查失败，停止追加修改，优先恢复正确性。

## 8. 测试要求

按项目替换测试清单：

- 数据完整性测试。
- 核心规则测试。
- UI 主流程测试。
- AI/NPC 合法性测试。
- 存档读写测试。
- 发布包 smoke test。

UI 类任务必须额外完成真实分辨率视觉验收。Headless 测试只能作为逻辑/加载验证，不能替代真实运行画面或截图检查。

## 9. AI 行为限制

AI 可以读取设计上公开的信息和自身状态。

AI 不得读取：

- 玩家隐藏信息。
- 未来随机结果。
- 未公开的资源或牌堆顺序。
- 不应由当前系统知道的调试状态。

如果项目允许“全知 AI”，必须在 GDD 和设置中明确说明。

## 10. UI 开发约束

- 首屏应服务于实际可玩流程，不默认做营销式落地页。
- UI 不遮挡核心玩法信息。
- 文本必须在目标平台常见分辨率下不溢出。
- 重要状态不能只靠颜色区分。
- 结算或失败界面必须解释原因和结果。
- 凡任务涉及 UI、游戏界面、牌桌布局、卡牌显示、底部操作区、Overlay、设置页、战绩页、音频/美术接入后的界面变化，完成条件必须包含真实分辨率视觉验收。
- 开发前必须检查窗口尺寸、stretch/scale 配置、根布局、固定控件尺寸和最小高度，并提前估算垂直空间是否足够。
- 开发后必须在实际运行画面或截图中检查默认窗口尺寸、`1280x720`、`1366x768`、`1600x900`、`1920x1080`。
- 每个尺寸至少确认：顶部状态栏完整可见，中央主要内容完整可见，底部玩家手牌/主要操作区完整可见且可点击，捕获区/侧栏不会把底部内容挤出屏幕，Overlay 的按钮完整可见且可点击，文字没有裁切、重叠或溢出。
- 底部手牌、操作按钮、状态提示或决策按钮被裁切是阻断级 UI 问题。
- 若当前环境无法做实际视觉检查，必须明确报告“未完成分辨率视觉验收”，不能把 UI 任务标为 Done，也不能声称 UI 验收通过。

## 11. 工作流

每次开发前：

1. 读取相关拆分 GDD。
2. 检查当前文件和 git 状态。
3. 明确本轮只改哪些模块。
4. 小步实现。
5. 运行相关测试或手动验证。
6. 更新 TaskBoard 状态。

每次开发后：

- 汇报改了哪些文件。
- 汇报验证结果。
- 汇报未完成或风险。
- UI 类任务必须记录各分辨率视觉验收结果；若无法检查，必须记录“未完成分辨率视觉验收”。

## 12. 异常处理

遇到以下情况停止继续写入：

- 文件编码无法确认。
- JSON/YAML 解析失败。
- CSV/TSV 列数不一致。
- 文本字段疑似损坏。
- ID 冲突。
- 资源路径不存在且不是明确占位。
- GDD、数据、代码规则冲突。
- 批量脚本影响超过一个核心数据文件但没有备份。
````
